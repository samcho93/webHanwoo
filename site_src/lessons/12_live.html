지금까지의 파이프라인은 영상을 끝까지 본 뒤 ID 를 정하는 오프라인 방식입니다. 축사 카메라(RTSP)를 연결해 실시간으로 추적하려면 “미래 프레임” 없이 마릿수를 세고 ID 를 유지해야 합니다. 이 레슨에서는 처음 일정 시간 동안 마릿수를 세고 소마다 외형을 등록한 뒤, 그 N 마리 안에서만 ID 를 배정하는 온라인 알고리즘과, 파라미터를 화면에서 바로 조정하는 프로그램을 만듭니다.

입력(파일 / RTSP / 웹캠) ─ 읽기 스레드: 최신 프레임만 유지, 끊기면 재연결
   → YOLO 검출 + BoT-SORT 추적 (프레임 간 연결)
   → ReID 임베딩 (4프레임마다, 가림 적은 박스만)
   → [등록 단계, 처음 60초]  마릿수 N 카운트 + 소마다 외형 갤러리 등록
   → [추적 단계]           N 개 개체 슬롯에 트랙 배정 · 뒤바뀜 교정 · 활동량 누적
   → 화면 표시 / CSV / 결과 영상

1. 오프라인과 무엇이 다른가

단계오프라인 (레슨 07b)실시간 (이 레슨)
마릿수 N영상 전체에서 동시 검출 수처음 enroll_s 초 동안 동시 검출 수 + 외형 군집, 이후 확실한 새 소가 보이면 증가
ID 배정긴 tracklet 부터 전체를 보고 탐욕 배정 + 반복 개선새 트랙이 confirm_s 초 외형을 모으면 “안 보이는” 슬롯과 헝가리안 매칭
뒤바뀜(swap)겹침 앞뒤 ±4초 외형 비교 후 tracklet 분리겹쳤다 떨어진 뒤 swap_post_s 초 외형을 모아 두 ID 교환 여부 판단
활동량앞뒤 프레임으로 중앙차분과거 데이터만 사용 (최근 0.5초 위치 vs 1초 전 위치)
지연없음 (처리 후 재생)새로 나타난 소의 ID 는 약 1초 뒤 표시

2. 등록 단계: 마릿수 세기

한 프레임의 검출 수는 오검출·가림 때문에 흔들립니다. 그래서 두 가지 방법으로 세고 비교합니다.

  • 안정적인 동시 검출 수 (n_sim): 신뢰도 ≥ count_conf 인 검출이 k 개 이상인 상태가 count_stable_s 초 이상 이어진 최대 k. 순간적인 중복 박스는 걸러지지만, 다른 소 뒤에 계속 가려진 소는 세지 못합니다.
  • 외형 군집 수 (n_clu): 등록 구간의 추적기 트랙마다 ReID 평균 임베딩을 구하고, 유사도가 높은 것부터 묶습니다. 단 같은 시각에 함께 보인 트랙은 절대 묶지 않습니다(cannot-link). 가려졌다 나타난 소도 셀 수 있지만, 자세에 따라 외형이 달라 보이면 한 마리를 둘로 셀 수 있습니다.

기본값 count_mode=max 는 둘 중 큰 값을 씁니다. 군집은 그대로 각 소의 초기 외형 갤러리가 됩니다. 마릿수를 정확히 알고 있다면 마릿수 N 에 직접 입력하는 것이 가장 확실합니다.

3. 추적 단계: N 개 슬롯 안에서 ID 유지

  1. 사라짐: 슬롯에 묶인 트랙이 release_s 초 안 보이면 슬롯을 비우고 마지막 위치·시각을 기억합니다.
  2. 복귀: 같은 추적기 트랙이 다시 나타나고 이전 슬롯이 비어 있으면 바로 되돌립니다.
  3. 새 트랙 배정: 비어 있는 슬롯들과 비용 행렬을 만들고 헝가리안 매칭.
    비용 = w·(1 − 외형 유사도) + (1 − w)·(이동거리 / 허용거리), 허용거리 = (기본 반경 + 초당 반경 × 사라진 시간) × 몸길이. 허용거리 × 게이트를 넘으면 배정 불가.
  4. 뒤바뀜 교정: 두 트랙이 겹쳤다(IoU ≥ 0.2) 떨어지면, 떨어진 뒤의 외형으로 “그대로” 와 “서로 바꿈” 의 유사도 합을 비교해 더 나은 쪽을 택합니다.
  5. 외형 교정: 묶인 트랙의 최근 3초 외형이 자기 슬롯보다 안 보이는 다른 슬롯과 훨씬 비슷하면(drift_margin) 그 슬롯으로 옮깁니다.
  6. N 증가: N 개 슬롯이 모두 보이는데, 다른 박스와 겹치지 않는 확실한 트랙이 grow_s 초 이상 배정되지 못하면 새 소로 보고 N 을 1 늘립니다.

외형 갤러리는 등록 때 외형(고정) + 최근 외형 60개로 구성하고, 다른 소와 겹친 직후의 crop 은 넣지 않아 갤러리가 오염되지 않게 합니다.

4. 실시간 입력: 지연이 쌓이지 않게

처리 속도가 카메라 fps 보다 조금이라도 느리면, 프레임을 순서대로 처리할 때 지연이 계속 늘어납니다. 그래서 스트림은 별도 스레드가 계속 읽으면서 가장 최근 프레임 하나만 남기고, 처리 스레드는 그 프레임을 가져갑니다(버린 프레임 수는 화면에 표시). 연결이 끊기면 1→2→4→5초 간격으로 다시 연결합니다. RTSP 는 기본으로 TCP 로 받아 패킷 손실로 화면이 깨지는 것을 줄입니다. 활동량은 프레임 번호가 아니라 실제 시각으로 계산하므로 프레임을 건너뛰어도 속도·거리가 맞습니다.

5. 프로그램 사용법

live.bat                                   # 또는 run.bat 메뉴 7
live.bat rtsp://admin:password@192.168.0.64:554/Streaming/Channels/101
python live_app.py --headless --source rtsp://... --save-video   # 화면 없는 서버에서
  • 입력 탭: 영상 파일 / RTSP 주소 / 웹캠, 원래 속도 재생, CSV·영상 저장, [마릿수 다시 세기]
  • 파라미터 탭: 항목에 마우스를 올리면 설명이 나옵니다. 검출·ID 배정·활동량은 즉시 반영, 추적기(BoT-SORT) 설정은 추적기만 재시작(개체 ID 는 슬롯이 유지), 카운트 설정은 [마릿수 다시 세기] 로 적용. 튜닝한 값은 [프리셋 저장] 으로 JSON 에 저장하고, configs/live_default.json 으로 저장하면 시작할 때 자동으로 불러옵니다.
  • 상태 탭: 마릿수 N, 보이는/사라진 소, 처리 fps, 개체별 상태·속도·이동거리·활동지수
  • 결과: outputs/live/<이름>_<시각>/ 에 tracks_live.csv(프레임별), summary_live.csv(개체별 요약), events.log, config.json(사용한 파라미터)

한계

  • 등록 구간에 소들이 뭉쳐 있거나 일부가 계속 가려져 있으면 처음 N 이 적게 잡힙니다. 자동 증가가 보완하지만, 마릿수를 알면 직접 입력하세요.
  • 실시간 방식은 미래 프레임을 쓸 수 없어 오프라인(레슨 07b)보다 ID 유지가 약합니다. 한우는 털색이 비슷해 오래 뭉쳤다 흩어지면 ID 가 바뀔 수 있습니다. 기록용 데이터는 저장된 영상을 오프라인으로 다시 처리하면 더 정확합니다.
  • 정답 라벨이 없어 정확도는 콘택트 시트로 눈으로 확인한 수준입니다. 장시간 확실한 ID 가 필요하면 귀표 번호 인식이나 해당 축사 영상으로 ReID 재학습을 더하세요.
  • RTSP 경로는 영상 파일을 스트림으로 보내 수신·끊김·재연결을 시험했습니다. 실제 카메라는 기종마다 주소 형식이 다릅니다.
